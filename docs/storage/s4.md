# S4 Storage

[S4 installation and GroundX configuration](../../README.md#using-s4). Run commands from the repository root.

These procedures require GroundX chart 0.2.8 or later with its default images and `fileAccess.enabled: false`. With file access enabled, inline storage credentials are rejected and the bucket must stay private; do not apply the anonymous-read policy below.

## Limits

- One replica, so no high availability ([chart values](https://github.com/rh-aiservices-bu/s4/blob/797911cbaa1b44fcaecfdfe69145a6a904ef7463/charts/s4/values.yaml#L4)).
- Thousands to tens of thousands of objects per bucket ([S4 FAQ](https://github.com/rh-aiservices-bu/s4/blob/797911cbaa1b44fcaecfdfe69145a6a904ef7463/docs/operations/faq.md#how-many-objects-can-s4-handle)).
- The image is built for `linux/amd64` only.
- Kubernetes health checks cover only the web UI port (5000), not the S3 port (7480) that GroundX uses.
- In S4 mode, large-file import and review (large-file delivery, off by default) refuse files larger than 5 GiB, the largest single upload S4 accepts, before uploading them. They also spool each upload to a temporary file in the pod's `TMPDIR` on top of the importer's own copy, so they need temporary pod disk of about twice the largest file for each upload in flight.
- Long object keys fail. S4 limits the whole key, path included, as sent URL-encoded: the limits are 246 bytes for a single upload and 210 bytes for a multipart upload. Each `/` counts as 3 bytes, and each non-ASCII character counts as its URL-encoded length (9 bytes for a 3-byte UTF-8 character, as in Chinese or Japanese), so such file names fail much sooner. A file name fails below those figures by the length of the path GroundX puts in front of it. Extraction trace capture saves on S4 from chart 0.2.8.
- The access key and secret key are fixed when S4 first starts on its volume. Restarting with different credentials does not change the stored keys.
- Bucket creation outside region `us-east-1` fails. GroundX services always use `us-east-1` for `s4` and ignore a configured region.
- Write-once (creating an object only if its key is absent) holds only for writers that do not overlap in time. Concurrent writers can both report success for the same new key; only one writer's content is kept.

## Migrating from MinIO or AIStor

Install S4 as [release `s4`](../../README.md#using-s4) before starting.

To move an existing MinIO store to S4, S4 must take over MinIO's URL as well as its objects. GroundX saves each file's full URL, including the store's host, with the document and inside processed files, and it reads and copies only files whose URL starts with its storage URL. Connected at `s4.eyelevel.svc.cluster.local:7480`, GroundX could no longer open or copy any document stored before the move. These steps copy every object with the same keys, set the public-read policy, and then hand Service `minio`, which GroundX's default storage URL `http://minio.eyelevel.svc.cluster.local` reaches, from MinIO to S4. GroundX's file, X-Ray, and page-image links are unsigned and rely on that policy, and GroundX sets it only when it creates the bucket itself. The copy carries neither object tags (GroundX does not read them back) nor the bucket policy, and a file whose name is too long for S4 fails to copy.

The steps cover a store installed by the [installation guide](../../README.md) in namespace `eyelevel`, with `file.existing.url`, `file.customDomain`, `file.serviceName`, and `file.bucketName` unset in your GroundX values, and S4 installed as release `s4`. If your values set any of them, S4 must answer at exactly the scheme, host, and port GroundX uses today instead; GroundX has not tested that.

1. Stop uploads to GroundX, then wait until no documents are still processing. Keep uploads stopped until step 7. Processing keeps writing files to MinIO, and a file written after the copy is not on S4 and is lost at the switch. If you cannot confirm that nothing is processing, do not migrate. This wait is required by the processing write path and has not been tested.
2. Copy the bucket with [rclone](https://rclone.org/) from a machine that can reach both stores. The S4 bucket is created in `us-east-1`:

   ```bash
   export RCLONE_CONFIG_SRC_TYPE=s3 RCLONE_CONFIG_SRC_PROVIDER=Minio
   export RCLONE_CONFIG_SRC_ENDPOINT=<minio-url>
   export RCLONE_CONFIG_SRC_ACCESS_KEY_ID=<minio-access-key> RCLONE_CONFIG_SRC_SECRET_ACCESS_KEY=<minio-secret-key>
   export RCLONE_CONFIG_DST_TYPE=s3 RCLONE_CONFIG_DST_PROVIDER=Ceph RCLONE_CONFIG_DST_REGION=us-east-1
   export RCLONE_CONFIG_DST_ENDPOINT=<s4-url>
   export RCLONE_CONFIG_DST_ACCESS_KEY_ID=<s4-access-key> RCLONE_CONFIG_DST_SECRET_ACCESS_KEY=<s4-secret-key>

   rclone mkdir dst:eyelevel
   rclone copy src:eyelevel dst:eyelevel --metadata
   ```

3. Allow anonymous `s3:GetObject` on the bucket's objects, the same policy GroundX sets on a bucket it creates:

   ```bash
   cat > public-read.json <<'EOF'
   {
     "Version": "2012-10-17",
     "Statement": [
       {
         "Effect": "Allow",
         "Principal": {"AWS": ["*"]},
         "Action": ["s3:GetObject"],
         "Resource": ["arn:aws:s3:::eyelevel/*"]
       }
     ]
   }
   EOF
   AWS_ACCESS_KEY_ID=<s4-access-key> AWS_SECRET_ACCESS_KEY=<s4-secret-key> \
     aws s3api put-bucket-policy --endpoint-url <s4-url> --region us-east-1 \
     --bucket eyelevel --policy file://public-read.json
   ```

4. Check the copy, in the same shell so that the `RCLONE_CONFIG_...` variables from step 2 are still set:

   ```bash
   rclone check src:eyelevel dst:eyelevel
   ```

   It exits 1 whenever a file name is too long for S4, because that file never copies. Read its output, and switch only if every difference it reports is a file whose name is too long for S4 and that you accept losing. Otherwise stay on MinIO and deal with the listed files first. A notice that some hashes could not be checked refers to objects MinIO stored in parts, which rclone compares by size only; it is not a difference.

5. Hand Service `minio` to S4. Save the MinIO store release's values, which going back needs, then uninstall the release; its volume claim and data stay. Set `STORE_RELEASE` to the release: `minio-cluster` for community MinIO installed by earlier versions of this guide, or `minio-tenant` for AIStor. `helm list -n eyelevel` shows it and its chart version, which going back needs; note both. Storage is unavailable until the new Service exists, and GroundX cannot read stored files until its upgrade in step 6 finishes, so run step 6 straight after this step.

   ```bash
   STORE_RELEASE=<store-release>
   helm get values "$STORE_RELEASE" -n eyelevel -o yaml > minio-store-values.yaml
   helm uninstall "$STORE_RELEASE" -n eyelevel
   kubectl -n eyelevel wait --for=delete service/minio --timeout=5m

   cat <<'EOF' | kubectl apply -f -
   apiVersion: v1
   kind: Service
   metadata:
     name: minio
     namespace: eyelevel
   spec:
     type: ClusterIP
     selector:
       app.kubernetes.io/name: s4
       app.kubernetes.io/instance: s4
     ports:
       - name: s3-api
         port: 80
         targetPort: 7480
   EOF
   ```

   `minio-store-values.yaml` holds the store's root credentials; keep it somewhere safe.

6. Point GroundX at S4 through the MinIO URL, then upgrade GroundX. Leave the port out of the URL: GroundX saved its URLs without one, and they must match exactly.

   ```yaml
   file:
     username: <s4-access-key>
     password: <s4-secret-key>
     existing:
       serviceType: s4
       url: http://minio.eyelevel.svc.cluster.local
   ```

7. Open a file, X-Ray, or page-image link of a document ingested before the move; it must load. That link does not use GroundX's S4 keys, so also ingest one small test document and check that it finishes processing. Then resume uploads.

To go back, stop uploads, delete Service `minio`, install the store release again under its old name from `minio-store-values.yaml` with the chart version you noted in step 5 (for AIStor installed by this guide, `minio/aistor-objectstore` 1.1.0; for community MinIO, the tenant chart with a server image you can pull, where the tested form is chart 7.1.1 as in step 6 of [Restoring Community MinIO from the Pre-Upgrade Snapshot](minio-migration.md#restoring-community-minio-from-the-pre-upgrade-snapshot), with `minio-store-values.yaml` in place of `minio-cluster-values.yaml`), restore your previous `file` settings, and upgrade GroundX. The store comes back on its kept volume claim, but files written only to S4 after the switch are not on MinIO.
