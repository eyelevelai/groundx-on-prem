### Stand-in

- Image `gx142-standin-celery:local` is `FROM public.ecr.aws/c9r4x6y5/eyelevel/extract:0.2.8` (USER 1001 kept), plus `/app/standin_celery.py`. It was loaded into gx142 with `minikube image load`.
- The stand-in Celery app runs on broker `redis://host.minikube.internal:6379/14`. Its task `standin.sleep60` sleeps 60 s.
- It matches the real download task's ack settings, which were read from the image's `/app/celery_agents.py` and `/app/tasks/download.py`: `acks_late=True`, `worker_prefetch_multiplier=1` and `task_reject_on_worker_lost=False`.
- It logs these with millisecond timestamps: `worker_ready`, `worker_shutting_down` (the signal received), `worker_shutdown`, `task_prerun` (TASK-START) and `task_postrun` (TASK-END).
- supervisord.conf is each chart's rendered conf with only `command=` changed on each `celery_worker_N`. `-A celery_agents.app` became `-A standin_celery.app`, and the queue became `gx142_q41_new` or `gx142_q41_base` so the two pods could run at the same time. Every other line, the ordering and the `[group]` section are as rendered:

```
< command=celery -A celery_agents.app worker -n %(ENV_POD_NAME)s-w1 --loglevel=INFO --concurrency=1 --queues=download_queue --prefetch-multiplier=1 --max-tasks-per-child=100
> command=celery -A standin_celery.app worker -n %(ENV_POD_NAME)s-w1 --loglevel=INFO --concurrency=1 --queues=gx142_q41_new --prefetch-multiplier=1 --max-tasks-per-child=100
(same for w2; base uses gx142_q41_base)
```

- The conf was mounted the same way the chart mounts it: a ConfigMap (`q41-<new|base>-supervisord`) with subPath `/app/supervisord.conf`.
- The Pod used the chart's pod/container securityContext (1001, non-root, drop ALL), the `POD_NAME` fieldRef env, `workingDir: /app`, the chart's start command and `terminationGracePeriodSeconds: 900`.

**Deviation (environment only):** on this machine `host.minikube.internal` (192.168.67.1) does not reach the host's Redis port; the connection timed out. Docker Desktop's host address does reach it: `192.168.65.2`, which is `host.docker.internal`, verified with a redis `PING` from a pod. Each pod therefore gets `hostAliases: host.minikube.internal -> 192.168.65.2`. The broker URL stays `redis://host.minikube.internal:6379/14`, and the Redis is the existing `redis-cache-1`, DB 14 only.

### Procedure (`run41.sh`, new and base in parallel)

1. Start `kubectl logs -f --timestamps` on the pod.
2. Enqueue `<c>-t1` and `<c>-t2` from a client pod using the same image, and wait until both show `TASK-START`, one per worker.
3. Wait 5 s, then run `kubectl --context gx142 -n gx142 delete pod q41-<c> --wait=false`.
4. Right after that, enqueue `<c>-t3`.
5. Run `kubectl wait --for=delete`, then `redis-cli -n 14 LLEN gx142_q41_<c>`.

## Discarded first run

The first run's stand-in task used Celery's default early ack. Worker w1 took t1 and also reserved t2, so w2 sat idle and the "two busy workers" precondition was never met. The idle w2 in the new pod even received t3 as SIGTERM arrived (the delivery was already in flight). That run does not test the claim and is not counted. The stand-in was rebuilt with the real download task's `acks_late=True`, and the run above is the valid one. Its raw output is in the scratchpad at `.../scratchpad/evidence/41/results-run1-invalid/`.
