# GX-142 task 4.2: extract-agent preStop run time against the 30 s slack

Run: 2026-11-02, local Docker, with the real `eyelevel/extract:0.2.8` Celery app. Redis is the existing `redis-cache-1`, DB 14 only. No AWS, no cloud.

## Result

| Workers N | Expected | Actual: preStop wall time (3 trials) | c per worker = (T - 5) / N | Slack used (of 30 s) | Pass/Fail |
|---|---|---|---|---|---|
| 1 | well under 30 s | 6.95 / 6.81 / 6.70 s (max 6.95) | 1.95 / 1.81 / 1.70 s | 23 % | Pass |
| 2 | well under 30 s | 8.46 / 8.41 / 8.75 s (max 8.75) | 1.73 / 1.70 / 1.88 s | 29 % | Pass |
| 3 | well under 30 s | 10.39 / 10.10 / 10.17 s (max 10.39) | 1.80 / 1.70 / 1.72 s | 35 % | Pass |

- **No tested worker count reaches 30 s; nothing to escalate.** The slowest run was 10.39 s at N=3, leaving 19.6 s of slack.
- Measured `c` is 1.70 to 1.95 s, almost all of it the `python -m celery -A celery_agents.app` import before each call.
- Model: `5 + N * c` with c = 1.95 s (worst trial) gives 6.95 / 8.90 / 10.85 s for N = 1 / 2 / 3. It reaches 30 s only at N >= 13 (5 + 13 * 1.95 = 30.35).
- Every trial got an `OK ... no longer consuming from agent_queue` reply from every worker, so each call reached a live worker. It did not fall through `|| true`.

The slack is 30 s because the rendered `terminationGracePeriodSeconds` is 900 and supervisord `stopwaitsecs` is 870 for extract-agent at N = 1, 2 and 3 in the new chart. The preStop runs inside the grace period, before SIGTERM. A preStop that ran past 30 s would eat into the 870 s that supervisord gives the workers to drain.

## Rendered inputs (new chart, worktree HEAD `3f4e5144`)

```
helm template t <chart> -f <chart>/tests/files/values.search-credentials.yaml \
  --set extract.enabled=true --set extract.api.enabled=true --set extract.agent.enabled=true \
  --set extract.agent.workers=<N>
```

Rendered preStop (`_helpers/app/extract-agent.tpl` line 303). The N=3 render was:

```
cd /app && export PYTHONPATH=/app && for i in $(seq 1 3); do python -m celery -A celery_agents.app control cancel_consumer agent_queue -d celery@${POD_NAME}-w${i} || true; done; sleep 5
```

N=1 and N=2 differ only in `seq 1 N`. The base chart (`7661506`) renders the identical preStop; GX-142 does not change it.

Rendered extract-agent worker program, one per N:

```
command=celery -A celery_agents.app worker -n %(ENV_POD_NAME)s-w<i> --loglevel=INFO --concurrency=2 --queues=agent_queue --prefetch-multiplier=1 --max-tasks-per-child=1
stopwaitsecs=870
[group:celery_workers]  programs=celery_worker_1[,celery_worker_2[,celery_worker_3]]
```

Grace is 900 at every N.

## Setup

- Images `gx142-standin-agent-n<N>:local` are `FROM public.ecr.aws/c9r4x6y5/eyelevel/extract:0.2.8` (USER 1001 kept). Each COPYs in two files:
  - `/app/supervisord.conf`, the rendered extract-agent conf for that N, unmodified;
  - `/app/config.py`, the chart's rendered `extract-config-py-map` with only the two broker URLs changed:
    ```
    <     broker="redis://cache.eyelevel.svc.cluster.local:6379/0",
    >     broker="redis://host.docker.internal:6379/14",
    <     metrics_broker="redis://cache-metrics.eyelevel.svc.cluster.local:6379/0",
    >     metrics_broker="redis://host.docker.internal:6379/14",
    ```
- The workers are the image's **real** `celery_agents.app`, not a stand-in app. They are started by the chart's rendered command, `/bin/sh -c 'export PYTHONPATH=/app && exec supervisord -c /app/supervisord.conf'`, with `POD_NAME=<container name>`. They sit idle on `agent_queue` in DB 14. The real app sets `global_keyprefix "{celery}"`, so the broadcast path, the key prefix and the import cost all match production.
- The preStop was run with `docker exec <c> /bin/sh -c '<rendered preStop>'`, timed by the host clock around the exec. There was one fresh container per trial, so every trial cancels consumers that are still active.
- The script waits for the workers to start, then 2 s more, before running the preStop. The app's own logging suppresses Celery's `ready` banner line, so the readiness grep never matched and each trial waited its full 120 s readiness window. The workers were therefore fully up, and every worker replied `OK`.

## Limits of this measurement

- The run used an unloaded local Docker Desktop VM with 12 vCPUs and no container CPU limit. A CPU-throttled pod, or one where the worker processes are busy, will import more slowly, so `c` will be higher.
- Broker trouble was not tested: an unreachable or slow Redis was out of scope. In that case each call could run up to Celery's connect and reply timeouts before `|| true`.
- Even at 2x the measured `c` (3.9 s), N=3 would take about 16.7 s, still under 30 s.
