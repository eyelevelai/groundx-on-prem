## Goals / Non-Goals

**Goals:**
- Render `inlineImages: true` in an engine block only when that engine's own value is `true`, so the setting is an operator opt-in and every other install renders the bytes it renders today (motivation and blast radius: `proposal.md`).
- Keep `src/groundx` and `helm/` byte-identical for the three chart files this change touches, and keep the committed snapshots equal to the chart base branch without ever regenerating them.

**Non-Goals:**
- No change to `groundx.engines`, `groundx.engine.settings`, `groundx.engine.create` or any shared helper; no Chart version bump (which release first carries the key is decided outside this change).
- No `fileAccess.enabled` logic, no storage-type or engine-locality logic, no new values default, no new Kubernetes resource, no edit to `.build/bin/validate-helm.sh`, and no new script.
- No consumer or documentation edits: cashbot-go reads the key and `groundx-studio-harness` documents it, each in its own change.

Producer contract confirmed: the rendered boolean key `engines.<engineID>.inlineImages` is specified in the workspace `contract.md`; the shape is not repeated here. Line references below are to the groundx-on-prem base `origin/0.3.0` at `c6804db1` unless another ref is given.

## Decisions

- **Invariant (opens every decision below).** A rendered `config.yaml`, and the `config-hash` annotation that hashes it, may differ from the base branch's only where an engine's own values set `inlineImages` to `true`. Storage type, engine service and engine locality are not the test, and neither is the presence of a snapshot line: a snapshot is acceptable only because the install it renders sets no value.
- **Where it is computed.** In the engine loop of `src/groundx/templates/resources/config-yaml.yaml`, beside the `maxImages` block (`config-yaml.yaml:206-208` at base), as a literal `inlineImages: true` line placed after `baseURL` and before `maxImages`. The check reads only the engine's own value, so no root context, storage lookup or helper call is needed. Alternative rejected: computing it in `groundx.engines` or `groundx.engine.settings` (`engines.tpl:1-33`, `engines.tpl:35-66`); those helpers also feed `config-models.yaml`, `extract.tpl` and `summary.tpl`, and a value added there would reach readers that never asked for it.
- **Boolean guard.** The template tests `and (kindIs "bool" (get $e "inlineImages")) (get $e "inlineImages")`. A plain truthiness test would treat any non-empty string as true, and the schema constrains only `engines.default` (`values.schema.json` `engines.properties.default`, no `additionalProperties: false` on `engines`), so a stray string on another engine name would otherwise render `true` and send page images to that engine. `eq (get $e "inlineImages") true` is not used because Go's `eq` errors on a string/bool comparison (helm v3.19.0: `error calling eq: incompatible types for comparison`) and `get` returns an empty string for an unset key. For every schema-valid value the result equals a plain truthiness test.
- **No derived default, no override.** The branch's earlier template derived `true` from `groundx.engine.create` plus `s3` storage, with an operator override. Both are removed: the maintainers' decision (Linear comments 5, 7 and 8 on GX-93) is that the chart enables the setting only when an engine's values set it. This removes the storage and locality logic, the second per-engine code path in `config-yaml.yaml`, and every snapshot change the derived default caused.
- **Schema.** `engines.default.inlineImages` stays `{ "type": "boolean" }` in both copies (already present on the branch). The type error for a string is `got string, want boolean`.
- **Documented opt-in limitation.** Setting `engines` replaces the implicit default engine (`engines.tpl:46-59`) and the schema requires `engineId`, so an install that has never set `engines` must declare the full `engines.default` block to opt in. `values.yaml` shows that block with the built-in engine's own settings (`google/gemma-3-4b-it` from `summary-inference.tpl:145-150`, `maxInputTokens` 100000 from `summary-inference.tpl:124-129`, `maxOutputTokens` 4096 from `summary-inference.tpl:131-136`, `dataType` `bfloat16` from `summary-inference.tpl:46-51`, `vision` true and `maxRequests` and `requestLimit` as twice the desired inference replicas from `engines.tpl:46-59`). A new top-level opt-in value was rejected: it would be a new public setting the ticket does not ask for.
- **Test placement.** The helm-unittest cases stay in `src/groundx/tests/resources_test.yaml` beside the `maxImages` cases, which already render the same template. Five cases remain: no value on the local `s3` engine renders no key; `true` on the local `s3` engine renders it; `true` on an `openai` engine with in-cluster storage renders it (catches a storage or locality rule); `false` on the local `s3` engine renders none; a string fails the schema. The fixtures `values.inline-images-s4.yaml` and `values.inline-images-remote-eyelevel.yaml`, and the four cases that checked the derived default (in-cluster MinIO and AIStor, S4, remote `eyelevel`, `openai` on `s3`), are deleted, because nothing derived remains to check. `values.inline-images-s3.yaml` and `values.inline-images-openai.yaml` stay in use. `helm/` has no `tests` directory and `helm/.helmignore` lists `tests`, so nothing ships in the chart. Every "no key" case also asserts its precondition (the `upload` service line and the engine's own line), because a fixture that sets `serviceType` without `file.existing.url` silently renders `minio` (`file.tpl:166-175`) and would pass for the wrong reason.
- **How a task check isolates one case.** The cases sit in a suite that also holds snapshot tests, so a whole-suite exit code cannot show that one named case passes. The check runs `helm unittest -f tests/resources_test.yaml -o JUnit --output-file` on a `mktemp -d` copy of `src/groundx` (helm v3.19.0) and a short `python3 -I` script reads the named `test` elements from the result file and requires `result="Pass"` for each. The unittest output stays in a temp file and is never displayed, because a failing case prints rendered manifest fragments.
- **Snapshot scope.** No snapshot file is edited. `golang_test.yaml.snap`, `metrics_test.yaml.snap` and `resources_test.yaml.snap` equal the base branch's, and the template's output for installs that do not set the value must keep matching them: `app/golang.yaml:65` and `app/metrics.yaml:121` hash the rendered `config-yaml.yaml`, so any stray line would change a `config-hash`. A task check runs `.build/bin/validate-helm.sh` (never `helm unittest -u`) with helm v3.19.0 first on `PATH`, restores the snapshot files from a pre-run copy if the run fails, and then requires `git diff` of the snapshot directory against `git merge-base HEAD origin/0.3.0` to be empty. The merge-base, not the moving `origin/0.3.0` tip, is the reference, so a later base advance cannot turn the check red for unrelated snapshot changes.
- **Gate versus the privileged-repo convention (conflict recorded, not resolved silently).** `openspec/config.yaml` records from GX-131 that a README-only change declared `check: n/a` instead of executing `validate-helm.sh` in this privileged repo. This change requires the rendered snapshots to equal the base, which only the gate can show, so one task check runs it, following the GX-36, FRA-145 and GX-49 precedent, with its output in a temp file and helm v3.19.0 and a verified `python` placed first on a temporary `PATH` directory. The reviewer should confirm that choice.
- **Mirror.** `helm/templates/resources/config-yaml.yaml`, `helm/values.yaml` and `helm/values.schema.json` are compared byte for byte by `verify_mirrors()` (`.build/bin/verify-storage-contract.py:144-155`, `:216-241`) on every gate run and by `cmp` in the task checks; no new drift check is added.
- **Compatibility class (producer).** The key is additive: with no value set the render is identical to the base, and a worker image that predates the setting ignores a rendered key. cashbot-go decodes its `config.yaml` with `yaml.NewDecoder(f)` then `Decode(v)` and never calls `SetStrict` in that package (`pkg/config/config.go:94-95@80228c493bd4a928c643eca3d2feecfbdbea740c`, `gopkg.in/yaml.v2 v2.4.0` at `go.mod:91@80228c493bd4a928c643eca3d2feecfbdbea740c`), and that library decodes non-strictly unless `SetStrict(true)` is called (`yaml.go:108-110` in `gopkg.in/yaml.v2@v2.4.0`). No versioning mechanism is needed. Activation needs a summary-client image that reads the key; the chart release that first carries the key is not named here.
- **Shared readers.** Other templates read `groundx.engines` (`config-models.yaml:3`, `app/summary.tpl:15,35,41`, `app/extract.tpl:84`) and none reads `inlineImages`. The extract agent copies the `default` engine only when `extract.agent.serviceType` is unset (`extract.tpl:84-90`) and then reads named fields (`extract-agent.tpl:29,37,118,122,126,193`), so an operator-set `inlineImages` on `engines.default` reaches no extract setting.
- **No ADR.** The decisions are local to one template and its tests; none is hard to reverse.

## Existing mechanisms

- Per-engine optional key in `config-yaml.yaml`: the closest mechanism is the `maxImages` block (`config-yaml.yaml:206-208` at base), an `if` on the engine's own value that renders a literal line. `inlineImages` follows its shape and position; reusing `maxImages` itself is impossible because it carries a number, not a switch.
- Derived default (`groundx.engine.create` plus `get $fs "storageType"`): the branch's earlier mechanism for the same responsibility of deciding the value. It is removed, not kept beside the operator value; `groundx.engine.create` stays because `app/summary.tpl:18,29` use it.
- Boolean schema entry: `vision` (`values.schema.json:159`) is the same shape; `inlineImages` is its sibling.
- Test fixtures: `values.engine-max-images-valid.yaml` and `values.engine-max-images-null.yaml` set the precedent of small per-feature fixtures beside `resources_test.yaml`; no new fixture is added, two of the branch's four are deleted.
- Mirror drift check: `verify_mirrors()` already covers all three files; no close existing mechanism is missing, so nothing is added.
- Commented example in `values.yaml`: no close existing mechanism found for an `engines` example; the comment follows the file's plain `#` block style.

## Risks / Trade-offs

- [An operator sets `inlineImages: true` on an engine outside the cluster and the worker then sends this install's page-image bytes to that engine's `baseUrl`] → explicit operator choice; the commented `values.yaml` example says so, and nothing in the chart sets it.
- [A page the worker cannot read fails the request and the document once the setting is on] → stated in the `values.yaml` comment; the behavior lives in the worker (cashbot-go) and matches an `openai-base64` engine today.
- [An operator who never set `engines` hits `missing property 'engineId'` when writing only `engines.default.inlineImages`] → documented in the example, which repeats the full block; covered by the task that writes the comment.
- [A non-boolean value on an engine name other than `default` is ignored silently, because the schema does not constrain those names] → the boolean guard keeps it from rendering `true`; the schema still rejects the `default` engine's string.
- [The gate takes minutes] → it is the only gate-backed check; the other checks render or unit-test one suite on a scratch copy. If a gate run is killed (for example by a timeout), remove any leftover `files/ocr/gcv-test.json` under both charts before re-running, because the gate refuses to overwrite it.

## Rollout and blast radius

- Order: merge any time. The chart renders the key only when an operator sets it; nothing reads it until a summary-client image that contains the cashbot-go change is deployed (`Chart.AppVersion` unless `summaryClient.image` is set). Publishing the chart is a separate privileged maintainer step outside this change.
- Affected installs: none until an operator sets the value. For an install that sets it, `helm upgrade` rolls every Go-service Deployment and the metrics Deployment once, because their `config-hash` annotations change. No stateful resource is touched.
- Rollback: remove the value or run `helm rollback` (the same Deployments roll once more); pinning `summaryClient.image` to an image without the worker change makes the worker ignore the key.
- Cross-service coordination and deferred items: see the workspace change's `tasks.md`.
