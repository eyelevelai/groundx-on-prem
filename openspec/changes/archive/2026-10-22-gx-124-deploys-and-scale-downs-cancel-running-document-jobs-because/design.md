# Design — GX-124: Default 900-second shutdown wait for the Go queue services

Grounded in `proposal.md`. Producer contract shapes confirmed — see the workspace `contract.md` for the `drainSeconds` touchpoint and the external-semantics assumptions.

## Goals / Non-Goals

- Goal: with `replicas.gracePeriod` unset, `pre-process`, `process`, `queue`, `summary-client` and `upload` render `terminationGracePeriodSeconds: 900` and their config blocks render `drainSeconds: 870`; an explicit value still wins.
- Non-goal: `groundx`, `layout-webhook` and the opt-in workers (`fileAccess`, `largeFileDeliver`, `postProcess`); any cashbot-go drain change; the autoscaler flag and the bundled Terraform; per-service tuning from measured job durations; the harness docs (second PR).

## Rollout & removal plans

- Compatibility class: **Additive at the shape level, behavior change at rollout.** The decomposer's `Additive` label is re-confirmed against the code: `values.schema.json` already accepts `gracePeriod` on all five services and the `drainSeconds` key is already rendered when `gracePeriod` is set, so no values file or config shape becomes invalid. What changes is the default, which restarts Deployments once and lengthens how long a busy pod takes to stop. No compatibility mechanism beyond the chart version is needed; the consumer is a tolerant reader (decision 6).
- Restart set: upgrading to a chart with this change restarts the Deployments listed in decision 4 once, through the `config-hash` annotation. Pods that are mid-job on upgrade are stopped under their old spec (30-second Kubernetes default, no drain), so a job in flight during that one upgrade can still be cancelled and redelivered once; upgrade when ingest is low or the queues are drained.
- Slower rollouts: once running, a busy pod of the five services can take up to 900 seconds to stop on a rolling update, scale-down or node drain. An idle pod stops at once (cashbot-go `pkg/server/queue.go:L410-L430` at `fe2738144`).
- Rollback: redeploy the previous chart. The five services return to the 30-second Kubernetes default unless `gracePeriod` is set, and the Deployments restart once more. No values change is needed first, because `gracePeriod` is accepted by both charts.
- No database, secret or SQL change. The SQL-review gate does not apply to this service. The schema-migration Secret changes only in the rendered `config.yaml` text it embeds (decision 5).

## Decisions

1. **Invariant.** A service's rendered grace-period fields equal its own explicit `replicas.gracePeriod` when it sets one and the 900/870 default when it does not, for each of the five services alike; they never take another service's value, and a service outside the five never renders them. Spec scenarios `catches` (a default added in the shared `golang.yaml` reaching `groundx`/`layout-webhook`; a sweep that defaults only some helpers; an override leaking into a sibling block) and `must not block` (an explicit value on one service with the other four on the default; five independent overrides) enforce both halves.
2. **Default inside each replicas helper, not in `golang.yaml`/`config-yaml.yaml`.** The ticket's preferred `else`-branch location was "not confirmed" and the plan gate chose the helpers. Each of `groundx.preProcess.replicas`, `groundx.process.replicas`, `groundx.queue.replicas`, `groundx.summaryClient.replicas` and `groundx.upload.replicas` gains one block, beside the existing `cooldown`/`hpa`/`min`/`max` defaults: `if not (hasKey $in "gracePeriod")` then `set $in "gracePeriod" 900`. The unchanged `hasKey` guards in `golang.yaml:L73-L75` and the five in `config-yaml.yaml` then render the default and the derived `drainSeconds` (`max(1, gracePeriod - 30)` = 870). Because `golang.yaml` loops over every Go service, a branch there would also have to exclude `groundx`, `layout-webhook` and the opt-in workers; the helpers are per-service, so they cannot reach them. Rendered output is identical to the `else`-branch approach. The PR body says so in one line.
3. **The five helpers match one pattern.** `pre-process.tpl`, `process.tpl`, `queue.tpl`, `summary-client.tpl` and `upload.tpl` each define `groundx.<svc>.replicas` with the same body: take `$in` from `.Values.<svc>.replicas` (or an empty dict), then `set` `cooldown`, `hpa`, `target`, `threshold`, `throughput`, `min`, `desired`, `max` when absent, then `toYaml`. Diffing each of the other four helpers against the `process` one, from its `define` line to its `toYaml` line with the service name normalised, shows the only difference is the `max` default (`pre-process` 24, `summary-client` 32, `upload` 24; `queue` matches `process` at 16), so no other branch of the pattern differs from `process`. The same insertion after the `cooldown` block is therefore valid in all five. The `.Values` map is mutated in place, as it already is for the existing keys; the added key is idempotent, and no template reads `.Values.<svc>.replicas.gracePeriod` directly (searched `src/groundx/templates` for `gracePeriod`; the readers are `golang.yaml` and `config-yaml.yaml` for these five services, and the api, celery, inference, supervisord and extract/workspace paths for other services).
4. **Restart list (render-derived).** Observed on 2026-10-22 with helm v4.2.3: comparing `helm template groundx src/groundx` with the same command plus `--set <svc>.replicas.gracePeriod=900` for the five services, document by document, the `config-hash` annotation changes on seven Deployments: `groundx`, `layout-webhook`, `pre-process`, `process`, `queue`, `summary-client`, `upload`; `terminationGracePeriodSeconds: 900` appears on the last five only, and `config-yaml-map` gains five `drainSeconds: 870` lines. A render of the helper-patched chart equals that explicit-900 render. With `--set metrics.enabled=true` the `metrics` Deployment also restarts (`metrics.yaml:L121` hashes the same file). With `largeFileDeliver` and `postProcess` enabled from the test values files, `large-file-delivery` and `post-process` restart too, with the hash line as their only change. `fileAccess` goes through the same `golang.yaml` loop and hash line; a render with it enabled was not run (unverified).
5. **Schema-migration Secret and snapshots (render-derived).** The pre-upgrade `<release>-schema-migration` Secret embeds `config-yaml.yaml`'s `stringData`, so on `--is-upgrade` renders it gains the same five `drainSeconds: 870` lines; the schema-migration Job is untouched. The `metrics-tls` Secret differs between any two renders (generated certificate) and is not affected by this change. Running the full suite (helm-unittest 1.1.2, same date) with the committed snapshots against a scratch copy of the chart carrying the five helper edits failed three suites: `golang_test.yaml`, `resources_test.yaml` and `metrics_test.yaml` (49 tests, 138 snapshot blocks in that run). The other 15 suites passed, including `api`, `celery`, `extract`, `inference`, `ranker`, `stream` and `workspace`. The failing blocks are `config-hash` changes on the golang Deployments, `terminationGracePeriodSeconds: 900` on the five, `drainSeconds: 870` in the config and schema-migration Secret blocks, and the four tests that asserted absence.
6. **Consumer is a tolerant reader.** cashbot-go decodes its config with `yaml.NewDecoder` and no `KnownFields` (`pkg/config/config.go:94`, `:125` at `fe2738144`), so an image that predates the drain feature ignores `drainSeconds` and keeps exiting at SIGTERM. The chart can therefore roll out ahead of, with, or behind the image. The spec carries this as a backward-compatibility scenario.
7. **Nothing blocks a 900-second termination in the chart.** `golang.yaml` sets no `strategy`, `minReadySeconds`, `progressDeadlineSeconds` or `preStop` (searched the file). Its optional PodDisruptionBudget is `minAvailable: 1` with `unhealthyPodEvictionPolicy: AlwaysAllow` on Kubernetes 1.26+, which limits how many pods may be evicted at once, not how long a terminated pod may take. `resources/hpa.yaml` shapes scale-down with `stabilizationWindowSeconds` and percent/pod policies and never reads the grace period. Kubernetes' own rolling-update defaults and its treatment of Terminating pods in rollout progress were not exercised here (unverified); the validation-EKS run observes a real rolling update.
8. **SQS lease release on drain is accepted as intended.** In cashbot-go, `drainEnabled := q.Cfg.DrainSeconds > 0` (`pkg/server/queue.go:L177`) is passed to `leaseVisibility`, which releases an interrupted message only when `drainEnabled && ctx.Err() != nil` (`:L274`). So on SQS installs the new default also turns on drain-time release of messages whose processing a drain interrupts. This is the behavior the existing opt-in already enabled and the same behavior the ticket asks for on Kafka, so no per-stream default is added. The PR body states it, because it is a change for SQS installs that never set `gracePeriod`.
9. **Kafka duplicate/stall question stays a pre-merge validation, not a code decision.** The contract records the Kafka rebalance assumption as `spike-required`: source read says a draining pod remains a group member until close, so a pod joining during a rolling update can take its partition and replay the in-flight message, and a draining pod handed a partition does not fetch from it. The chart cannot change this, so the plan adds an explicit validation task (before and after, same method, validation EKS only) and, if concurrent duplicates or stalls are confirmed, the ticket author decides before merge whether the services' redelivery checks are safe under concurrency.
10. **Autoscaler cap documented, not changed.** On node scale-down the effective wait is the smaller of `gracePeriod` and the cluster autoscaler's `--max-graceful-termination-sec`, documented as default 600 (kubernetes/autoscaler `cluster-autoscaler/FAQ.md:1083` at `22575f5c8af3edd9a10ca10d7d9edef68d2982cd`, read this session). The same sentence, and the claim that the bundled EKS Terraform leaves it unset, is already in the harness `skills/groundx-on-prem/references/values-yaml.md:L420` on `main` (`a0dafadf`); a search of this repo for `graceful-termination` found no occurrence, consistent with unset. The cap is documented in the harness PR per the ticket author's "document only" comment.
11. **Tests, one place per behavior.** The new cases extend the two suites that already render these templates: `golang_test.yaml` (default on `summary-client`, an override on `process` leaving `upload` on the default, and `groundx`/`layout-webhook` still rendering none) and `resources_test.yaml` (every one of the five config blocks renders `drainSeconds: 870` when unset; the two isolation cases use a non-default value so an override cannot equal the default). The `groundx` and `layout-webhook` cases select the Deployment with `spec.selector.matchLabels.app`, because a Service with the same `metadata.name` is in the same template and makes a name selector ambiguous. The five config blocks are covered by one case because all five defaults come from separate helpers and a missed helper shows as one missing `drainSeconds`. Explicit assertions stay alongside the snapshots because the snapshots are hand-patched in this change and could freeze a wrong render. Existing assertions that required absence are inverted in place, not duplicated. Both suites also hold snapshot and credentials-fixture cases, so a per-task check runs the whole file with the OCR fixture the gate normally generates (`src/groundx/files/ocr/gcv-test.json`, removed afterwards).
12. **Snapshots hand-patched in a separate commit.** The affected `__snapshot__` blocks (golang, resources, metrics) are edited from the diff a plain `helm unittest` prints, never `-u` (repo `AGENTS.md`: `-u` drops required empty-render labels). Hash values come from the render, never typed: within one test the old `config-hash` repeats across Deployments and maps to one new value, so each replacement is a literal old-to-new substitution taken from the diff. The check is a plain `helm unittest` over the whole suite, which must pass with no snapshot written, plus `.build/bin/verify-helm-snapshots.py`.
13. **Local gate.** On this Windows machine `.build/bin/validate-helm.sh` stops at its plugin-version step (observed on the unchanged branch: it reports the helm-unittest plugin not found under `%APPDATA%\helm\plugins`, although `helm plugin list` shows `unittest 1.1.2`), so the full gate is run in WSL before push. `helm unittest` itself, `verify-helm-snapshots.py` and `verify-storage-contract.py` do run here, and the task checks use them directly. The whole suite takes about two and a half minutes on this machine.
14. **Spec delta.** `specs/queue-service-grace-period/spec.md` renames and modifies the "No gracePeriod set" requirement (it no longer holds), modifies the drainSeconds requirement (its summaryClient-only scenario) and the sweep-consistency requirement, and leaves the override and floor, schema, deploy-order safety and mirror requirements as they are. Per-service override isolation is kept in every modified requirement.
15. **No ADR.** The decisions above are local to one chart helper pattern; the helper-versus-`else` choice is recorded in decision 2 and the PR body.
16. **Pattern capture.** `openspec/config.yaml` `context:` already carries the helm unittest, snapshot and mirror conventions this change uses. The one new convention (the OCR fixture needed to run `golang_test.yaml`/`resources_test.yaml` outside the gate, and `documentSelector` ambiguity between a Deployment and a Service of the same name) is test-authoring detail kept in this design, not added to `context:`.
