## Goals / Non-Goals

Goals: the README-documented OpenSearch install trusts only operator-supplied certificates and users; the GroundX chart carries the operator CA to the Golang pods that call OpenSearch and fails closed without it. Non-goals: passwords and rotation (GX-75), the application user's `all_access` role, a NetworkPolicy, externally hosted OpenSearch, the `src/opensearch` wrapper chart, the Terraform operator's OpenSearch install (`terraform/groundx-operator/.../search/opensearch.tf` still passes `OPENSEARCH_INITIAL_ADMIN_PASSWORD` to the upstream chart; it is not the documented README route and is not changed here), release tarballs. See proposal.md for why.

Wording correction to the proposal's Impact line: `verify_mirrors()` in `.build/bin/verify-storage-contract.py` byte-checks `templates/` and the `MIRRORED_FILES` list, which includes `values/opensearch/values.yaml`, `values.yaml` and `values.schema.json`. This change adds `src/groundx/tests/files/verify-opensearch-tls-values.sh`, which checks the seed values themselves, and wires it into `validate-helm.sh` next to the probe-mirror check.

## Spike results (read-only: `helm pull` of upstream chart 2.23.1 and `docker run --rm --entrypoint cat|sh` on image digest `sha256:8e95a30fe67dc3d92b85924e46cd299bc83fe2716e100bcad30e7e3a0b199b00`; no OpenSearch process was started)

1. **Demo installer.** The image's own `config/opensearch.yml` has no security block. The entrypoint runs `install_demo_configuration.sh -y -i -s` unless `DISABLE_INSTALL_DEMO_CONFIG=true` (`opensearch-docker-entrypoint.sh`, `setupSecurityPlugin`). Separately, the upstream chart's default `config."opensearch.yml"` (`values.yaml:49-98` of chart 2.23.1) carries `allow_unsafe_democertificates: true` (`:74`), `admin_dn: CN=kirk,...` (`:78`) and `roles_enabled: ["all_access", "security_rest_api_access"]` (`:83`), and the seed values file does not override `config`, so the README install gets those from the chart. Decision: override `config."opensearch.yml"` entirely and set `extraEnvs: DISABLE_INSTALL_DEMO_CONFIG=true`.
2. **`OPENSEARCH_INITIAL_ADMIN_PASSWORD`.** It is read only by the demo-installer branch of the entrypoint, so with the installer disabled it is inert. The README's `opensearch-admin` Secret and `opensearch-admin.values.yaml` are removed. GX-75's "requires `OPENSEARCH_INITIAL_ADMIN_PASSWORD` at every start" statement no longer applies to a new-style install; it still applies to an existing release not yet moved to this configuration (upgrade note).
3. **Image `internal_users.yml` is a published credential.** With the installer disabled, the first security-index load reads `config/opensearch-security/internal_users.yml` from the image. Its `admin` hash verifies against the password `admin` (read-only check: `docker run --rm --entrypoint sh <image@sha256:8e95a30f...> -c "awk '/^admin:/{f=1} f&&/hash:/{print \$2; exit}' config/opensearch-security/internal_users.yml"`, then `crypt("admin", hash) eq hash` in Perl, with `crypt("notadmin", hash)` as the negative control; the hash is not copied into the repo), and it defines six more demo users. Disabling the installer alone would therefore replace the demo certificate with a public admin password. Decision: mount an operator `internal_users.yml` from a Secret via the upstream chart's `securityConfig.internalUsersSecret` (subPath mount of that one file, `statefulset.yaml:197-201,452-456`), containing only the `admin` user (`backend_roles: ["admin"]`, which the image's `roles_mapping.yml` maps to `all_access`). The GroundX application user is created through the REST API as today.
4. **`restapi.roles_enabled`.** The image config has no value; the chart default includes `all_access` (item 1). The seed keeps `["all_access", "security_rest_api_access"]` explicitly, so the admin user (mapped to `all_access`) keeps REST API access.
5. **Secret mounts in chart 2.23.1.** `secretMounts: [{name, secretName, path, subPath?}]` renders a `secret` volume (`statefulset.yaml:166-171`) and a mount at `path` (`:488-493`). A whole Secret mounted at a directory gives one file per key. Pod runs `runAsUser: 1000`, `fsGroup: 1000` (`values.yaml:316-318`), so Secret files are group-readable by the OpenSearch user.
6. **Not verifiable without running the server** (covered by the human-run live gate, tasks group 6): that the node boots with these settings; that `plugins.security.nodes_dn` is required or optional for a single node (the seed sets `CN=opensearch-node` to match the documented node-cert subject); that hostname verification is satisfied for HTTP clients by the SAN; that `hash.sh` run via the image prompts and prints a hash.

## Decisions

- **Invariant (gate class: render guard and values check).** A certificate whose private key is public, and a user whose password hash is public, authenticate to nothing; and the chart never renders a GroundX config for the chart-deployed OpenSearch that has no CA to verify it against. The spec carries the catching and must-not-block scenarios for both.
- **Producer contract (fixed names; cashbot-go builds against these):**
  - values key: `search.caSecretName` (string, default `""`; mirrors `fileAccess.caSecretName`).
  - Secret data key: `ca.crt`.
  - volume and mount name: `search-ca`; mount directory `/var/run/groundx/search-ca`, read-only; file `/var/run/groundx/search-ca/ca.crt`.
  - config.yaml key: `ai.aws.search.caFile` (string path), rendered only when `search.caSecretName` is non-empty.
  - Applies to every Deployment in `templates/app/golang.yaml` (`groundx`, `process`, and the other Golang services), not only the two OpenSearch callers, because the template renders one shared pod shape; unused mounts are harmless and the proposal approved this scope.
  - Producer contract shapes confirmed in code — see `contract.md` (written by the orchestrator).
- **Guard placement.** `groundx.search.caSecretName` helper in `templates/_helpers/services/search.tpl` fails when `groundx.search.create` is `true` and the value is empty; `config-yaml.yaml` calls it next to the GX-75 password checks (so it fires even when every Golang service is disabled). `groundx.search.caMount` / `caVolume` helpers follow the `fileAccess.caMount`/`caVolume` shape (`_helpers/app/file-access.tpl:198-216`) and are included in `golang.yaml` beside them.
- **OpenSearch seed values.** Operator Secrets: `opensearch-tls` (`ca.crt`, `node.crt`, `node.key`) mounted at `/usr/share/opensearch/config/certs`; `opensearch-internal-users` (`internal_users.yml`). The admin certificate and key are held by the operator and never mounted into the pod; the server needs only the DN (`CN=gx-opensearch-admin`). This departs from the proposal wording "each read from a Kubernetes Secret" for the admin certificate only: reading it from a Secret is the operator's own choice, but a mounted admin key would widen what a pod compromise yields. Transport `enforce_hostname_verification: false` because the seed is single-node (`replicas: 1`, `singleNode: true`); trust is the operator CA plus `nodes_dn`. HTTP clients verify the node certificate's SAN `<serviceName>-cluster-master.<ns>.svc.cluster.local` (the host `groundx.search.serviceHost` renders).
- **Chart version pin.** The README `helm install` gains `--version 2.23.1`, the version the spike read and the one `src/opensearch/Chart.yaml` and the Terraform operator already pin.
- **Existing installs.** The security index lives on the data volume: the new `internal_users.yml` is read only on first initialization of a new volume, so an existing install keeps its stored users, including the image's six non-admin demo users with published hashes. The README upgrade step tells the operator to remove those from the backed-up `internal_users.yml` before the `securityadmin` upload. Existing installs also keep their admin password; only certificates, the admin DN and the installer switch change on restart.
- **Rollout and rollback.** Order: create the Secrets; upgrade the OpenSearch release (restart); set `search.caSecretName` and upgrade GroundX (render now fails without it). Older `groundx`/`process` images ignore `caFile`: those that skip verification keep working against the new certificates, but those that trust only public CAs reject the demo certificate and the private CA alike, so they already fail before the OpenSearch restart and stay failing until `groundx` and `process` are upgraded to images that read `caFile` (see README "Upgrading an Existing Install" steps 1 and 2). Only images with the GX-90 cashbot-go change verify against the operator CA. Rotation of any certificate is a restart: OpenSearch first, then `groundx`, then `process`. Rollback: revert the values file and `search.caSecretName`; data and users are untouched, but reverting re-enables the demo configuration.
- **Tests.** One new helm-unittest suite (`tests/search_ca_test.yaml`) for guard, `caFile`, mount and no-mount; existing suites gain the fixture CA and only snapshots that show the new volume/mount/`caFile` are hand-patched, never `-u`. A shell check (`verify-opensearch-tls-values.sh`) covers the seed values; the hand-synced mirrors are byte-checked by `verify_mirrors()` through `MIRRORED_FILES`.
- **ADR.** None: the decisions above are local to this change and recorded here.
- **Config context.** `openspec/config.yaml` `context:` gains the GX-90 convention (the hand-mirrored values files are byte-compared by `verify_mirrors()` through `MIRRORED_FILES`, and `verify-opensearch-tls-values.sh` checks the seed values themselves).
