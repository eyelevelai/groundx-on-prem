## Goals / Non-Goals

Goals: a layout-inference pod deleted before or during model initialization never starts Celery; a pod deleted after start keeps GX-66's warm shutdown; every other inference render stays byte-identical. Non-goals and accepted residual risks are in `proposal.md` (decision A linger, init-to-main boundary window, `shareProcessNamespace` rejected). Workspace-level decisions are recorded in the workspace change `design.md`.

## Decisions

- **Settings-driven, layout-inference only.** `groundx.layout.inference.settings` keeps its `execOpts` key, now `exec` (it was `python /app/init-layout.py && exec`), and gains `initCommand`, the string `python /app/init-layout.py`. `inference.yaml` emits the `init-layout` init container only when `initCommand` is set; every other service's settings carry no `initCommand`, so their renders stay byte-identical (the empty `execOpts` default is untouched).
- **Init container position: last.** `init-layout` is appended after `download-model`, because it needs the model cache that `download-model` populates and the `wait-for-*` containers gate dependencies it uses. Order is `wait-for-cache`, `wait-for-file-storage`, `wait-for-metrics`, `create-symlink`, `download-model`, `init-layout`.
- **Init container context mirrors the main container.** Same image and pull policy, `workingDir`, `envFrom` workload secrets, `POD_NAME` and CA env, container security context, the same `resources` (see below), and the `config-models`, `config-volume`, `model-volume` and CA mounts. `supervisord-volume` is not mounted (init does not read it). The main container's probes and ports stay on the main container only.
- **`PYTHONPATH` stays exactly as today; no container `env` is added.** The main container keeps the chart's existing `/bin/sh -c` form with its `{{ $wd }}` templating, now `export PYTHONPATH={{ $wd }}:$PYTHONPATH && exec supervisord -c {{ $wd }}/supervisord.conf` (rendered `/app` for layout-inference); it contains no `init-layout.py`. The init container runs `/bin/sh -c "export PYTHONPATH={{ $wd }}:$PYTHONPATH && exec python {{ $wd }}/init-layout.py"`. A hard-set env `PYTHONPATH=/app` is rejected because the nvcr TensorFlow base image may set its own `PYTHONPATH`, which `$PYTHONPATH` in the export preserves. `exec` replaces the shell immediately, so `supervisord` (and `python` in the init container) is still PID 1 and receives SIGTERM itself.
- **Main command keeps the shell wrapper with `exec`.** `init-layout.py` failing stops the pod before the main container starts (init containers gate app containers), preserving the old `&&` behavior.
- **Init container has no signal wrapper (decision A).** The shell is replaced by `exec python`; a deletion mid-init waits for the script to finish or the grace period to expire, taking no tasks.
- **Init container gets the main container's resources, GPU included.** It renders the same `groundx.renderContainerResources` call on the same `$rs`, so `nvidia.com/gpu` and the `deviceType: cpu` path (no GPU) match the main container. Kubernetes does not sum init and app requests and reuses the init container's allocated devices for the app container, so this keeps today's GPU/model-load behavior at no extra pod cost. The chart test asserts the init container's GPU request and limit (cuda default) and the absence of one in cpu mode.
- **Mirror and snapshots.** `src/groundx/templates/**` changes are copied byte-for-byte into `helm/templates/**` (`verify_mirrors()` in `.build/bin/verify-storage-contract.py` enforces it). `src/groundx/tests/__snapshot__/inference_test.yaml.snap` is hand-patched; `helm unittest -u` is never used.
- **Lifecycle test (hand-run, minikube).** `src/groundx/tests/e2e/` is not used because `helm unittest` scans `tests/`; the script lives at `bin/tests/layout-inference-lifecycle/` with its stand-in `Dockerfile.layout-inference-stub` beside it, outside any path `bin/container` publishes, built only into minikube's docker (`eval $(minikube docker-env)`), never pushed. The stand-in image installs the real pip `supervisor` and real `celery` + `redis`; the chart's unedited rendered `supervisord.conf` drives them (`celery -A document.celery_process.app worker ...`). Only two things are stand-ins: `init-layout.py` (sleeps a configurable time, exits 0) and a minimal `document/celery_process.py` Celery app with one dummy task and an in-cluster Redis broker. The script deploys an in-cluster Redis, keeps enqueuing tasks throughout, and measures consumption from the broker/result side (tasks completed in the result backend and queue depth), so "zero tasks taken after deletion" is measured, not assumed. It runs `helm template` for `inference.yaml` plus `layout-supervisord-conf`, edited only through Helm `--set` values (image, `layout.inference.deviceType=cpu`, dependency endpoints, storage class), then asserts: (1) delete during init leaves the broker queue undrained and no task consumed by that pod; (2) delete after start drains warm: in-flight task finishes, worker exits within the grace period. Run against the current chart it fails assertion (1), against the fix it passes. It is not wired into pre-push or CI.
- **ADR.** None; the trade-offs above are recorded here and in `proposal.md`.
- **Producer contract shapes.** No cross-service contract; none to confirm.

## Rollout

A chart upgrade restarts the layout-inference Deployment once. Rollback is a chart rollback. No migration.
