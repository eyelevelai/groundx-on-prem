## Goals / Non-Goals

Goals: let an operator deliver `search.password` and `search.privilegedPassword` through the cluster credentials Secret instead of values, without the chart ever supplying a search password of its own. The authority is the current GX-75 Linear body and the 2026-10-07 maintainer decision recorded in `proposal.md`.

Non-goals: a new Secret-reference values key (`existingSecret`-style), a new template or Secret resource, any `values.schema.json` change, any change to `cluster.secrets` defaults, and any change to the published-default rejection, the ingest exemption, the literal removal or the Terraform validation from the first iteration.

## Decisions

**Invariant: the chart never renders a search credential that it chose itself or that is a published default; an unset credential is rendered as unset so the cluster Secret can supply it.** The check is the meaning, not the token "no `fail` on empty": deleting the empty-value failure while a helper `dig` default (or any literal) fills the gap would pass the token and violate the meaning. The spec carries the two scenarios that test this: a "catches" case (both passwords empty renders no search `password:` line, and a published default still fails next to an empty credential) and a "must not block" case (empty renders without error).

**Remove only the two empty-value failures, in `groundx.search.password` and `groundx.search.privilegedPassword`.** Each helper keeps its `mode: ingest` exemption and its `bannedPasswordHashes` rejection (`src/groundx/templates/_helpers/services/search.tpl:93-118@858753ac`). With the empty failure gone, an empty value returns an empty string.

**No change to `config-yaml.yaml`.** Both password lines are already guarded by `ne (include ...) ""`, so an empty helper result drops the `password:` line (`src/groundx/templates/resources/config-yaml.yaml:155-157` and `:255-257@858753ac`). The two bare `include` calls at `:76-77` stay, so the published-default rejection still runs when no Golang service is rendered.

**The Secret route needs no template wiring, only `cluster.secrets`.** Every Golang Deployment adds an `envFrom` `secretRef` for each name in `cluster.secrets` (`src/groundx/templates/app/golang.yaml:27-36` and `:135-141@858753ac`, names resolved by `groundx.secrets` at `src/groundx/templates/_helpers/main.tpl:197-205@858753ac`). `cluster.secrets` had no default at `858753ac` (`src/groundx/values.yaml:4-13`), so the route is opt-in: an operator who relies on the Secret must list `eyelevel-secret-credentials` there. The default is not changed to inject it automatically, because that would alter every install's pod spec for a ticket that did not ask for it. Code-grounding finding: the premise that the Golang pods receive the Secret holds only when `cluster.secrets` lists it; the README and the spec say so.

**Environment names are pinned by the approved plan for this change: `SEARCH_PASSWORD` for `AI.AWS.Search.Password` and `SEARCH_INIT_PASSWORD` for `Init.Search.Password`.** `proposal.md` carries the earlier draft name `SEARCH_PRIVILEGED_PASSWORD` for the second one; the pinned name wins and the proposal needs a one-word revision to match. The API image that reads them (cashbot-go, same level, not yet merged) is a dependency of this change, not an existing fact: the established loader prefers a non-empty values field and otherwise reads the environment variable (`pkg/config/env.go:47-53` in cashbot-go at `4dc076f26`), and an empty variable is the same as an unset one.

**The sample Secret carries the two keys with empty values.** A non-empty placeholder would be a working, unvalidated credential for anyone who applies the sample unchanged: the published-default rejection looks at values only, so it never sees Secret content, and when its login is rejected the GroundX API creates the application user with whatever `AI.AWS.Search.Password` it received, using the admin credential (`pkg/orchestrate/aws/client.go:391-422` in cashbot-go at `4dc076f26`). An empty value is inert: the API then has no password and fails at login rather than succeeding with a published one. The two prereq files (`src/groundx/prereqs/secret/values.yaml` and `helm/prereqs/secret/values.yaml`) were byte-identical at `858753ac` and stay so; `verify_mirrors()` compares only the `templates/` trees, so this task's check compares the two values files itself.

**Rollout, blast radius, rollback.** The change relaxes a render-time check, so no install that sets both values stops rendering and the rendered config for such an install is unchanged; no pod rolls unless an operator changes values or the Secret. The one behavior change: an install that supplies neither a value nor a Secret key now renders, and the failure moves to runtime (the GroundX API cannot log in to OpenSearch). That is the accepted tradeoff of the Secret route and is why the README states that Secret-delivered passwords are not render-validated. The Secret route works only once the API image that reads `SEARCH_*` is deployed; until then an operator who leaves values empty and relies on the Secret gets a runtime login failure, and operators who keep setting values are unaffected in either order. Rollback is reverting the chart; the empty sample keys are inert. No stateful resource, migration or OpenSearch data is touched; no DB-mutating task exists.

**Compatibility class: Additive for the contract, with one relaxed guard.** As a CONSUMER of the `SEARCH_*` names, this chart reads no new field and tolerates the API image gaining them. The values surface only becomes more permissive (empty is valid), so no existing values file breaks. The Terraform operator path is unchanged: it still takes both passwords as values and keeps requiring them, so the Secret route applies to the direct-helm install only.

**Tests live in one dedicated suite.** `src/groundx/tests/search_credentials_test.yaml` holds every search-credential case (empty renders, published default rejected, ingest, and the `cluster.secrets` envFrom premise), asserts on rendered text with no `matchSnapshot`, and does not need the Google OCR fixture the large `resources_test.yaml` needs. The cases that asserted an empty password fails moved out of `resources_test.yaml` and were reversed. Snapshots are not expected to change (an empty search password could not render before this change, so no snapshotted render used one, and the shared fixture sets the passwords explicitly); if one does, it is hand-patched and verified without `-u`, per `AGENTS.md`, never regenerated.

**Context correction.** `openspec/config.yaml` says the search fixture "is required because the chart has no default search passwords"; after this change a render without the fixture succeeds, so that sentence is reworded to say the fixture supplies explicit test credentials.

**ADR: none.** The decision is a small relaxation within an existing mechanism (`cluster.secrets`), recorded here; there is no hard-to-reverse architecture choice.

Producer contract shapes: not applicable (CONSUMER only); the `SEARCH_*` names are defined by cashbot-go and recorded in the workspace contract.
