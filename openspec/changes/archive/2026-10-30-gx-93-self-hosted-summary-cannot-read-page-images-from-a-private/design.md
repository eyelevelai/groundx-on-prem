## Goals / Non-Goals

**Goals:**
- Render `inlineImages: true` on the chart's own summary engine when files live on `s3`, let an operator override it per engine, and leave every other install's output byte-identical (motivation and blast radius: `proposal.md`).
- Keep `src/groundx` and `helm/` identical for the three files this change touches, and keep the committed snapshots truthful without regenerating them.

**Non-Goals:**
- No change to `groundx.engines`, `groundx.engine.settings` or any other shared helper; no Chart version bump (which release first carries the key is decided outside this change).
- No `fileAccess.enabled` logic, no new values default, no new Kubernetes resource, no edit to `.build/bin/validate-helm.sh`, and no new script.
- No consumer or documentation edits: cashbot-go reads the key and `groundx-studio-harness` documents it, each in its own change.

Producer contract: the rendered boolean key `engines.<engineID>.inlineImages` is specified in the workspace `contract.md`; the shape is not repeated here. Line references below are to the groundx-on-prem base tip `147d5aa0834632bbf679eaf73f8c3639ac9d6027` unless another ref is given.

## Decisions

- **Invariant (opens every sweep decision below).** A snapshot line `inlineImages: true`, and a changed `config-hash`, may exist for a label only if that label's resolved engine passes `groundx.engine.create` and its `upload.service` is exactly `s3`. The label's name and the bare token `s3` are not the test: `extract.oai` renders `s3` with an `openai-base64` engine and must stay unchanged, and every label that renders `minio` must stay unchanged.
- **Where it is computed.** In the engine loop of `src/groundx/templates/resources/config-yaml.yaml`, using `groundx.engine.create` (`_helpers/engines.tpl:68-72`) and `get $fs "storageType"`, the same expression that feeds `upload.service` (`config-yaml.yaml:725`) and the same `eq ... "s3"` form `file.tpl:208` uses. Rationale: the shared helpers also feed `config-models.yaml`, `extract.tpl` and `summary.tpl`, which must never see a derived key. Inside the loop `.` is not the root, so the call passes `$` as `root`.
- **Key position.** `inlineImages` renders after `baseURL` and before the `maxImages` block, which keeps the optional engine keys in the alphabetical order the block already follows. The four hand-patched `resources_test.yaml.snap` lines and the regexes in `resources_test.yaml` assume this position.
- **Override semantics.** A boolean `engines.<name>.inlineImages` decides: `true` renders `inlineImages: true`; `false` omits the key, which follows the `maxImages` null-omit precedent (`config-yaml.yaml:205-207`) and keeps opt-out installs free of a new line. Absent, null, or a non-boolean leaves the derived default in force. The template reads the value only through `kindIs "bool"`, because other engine names are not constrained by the schema and a stray string must never reach the rendered YAML. Alternative rejected: rendering `inlineImages: false`; it adds a line the consumer treats the same as absence and makes the opt-out render differ from an install that never had the key.
- **Schema.** `engines.default.inlineImages` is `{ "type": "boolean" }`, not `["boolean", "null"]`, matching the approved plan's "boolean" entry; a null on another engine name is handled by the kind check above. The type error text for a string is `got string, want boolean`.
- **Documented opt-out limitation.** Setting `engines` replaces the implicit default engine (`engines.tpl:46-59`) and the schema requires `engineId`, so on an install with no `engines` section, `engines.default.inlineImages: false` alone fails validation with `missing property 'engineId'`. Opting out needs the full `engines.default` block, or pinning `summaryClient.image` to an image that predates the worker change. This is stated in the `values.yaml` example and covered by task 1.2's check; it is not worked around, because a new top-level opt-out value would be a new public setting the ticket does not ask for.
- **Test placement.** The helm-unittest cases are folded into `src/groundx/tests/resources_test.yaml` beside the `maxImages` cases, with four fixtures under `src/groundx/tests/files/` (`values.inline-images-s3.yaml`, `-s4.yaml`, `-remote-eyelevel.yaml`, `-openai.yaml`); `helm/` has no `tests` directory and `helm/.helmignore` lists `tests`, so nothing ships in the chart. Every "no key" case also asserts its precondition (the `upload` service line and the engine's own line), because a fixture that sets `serviceType` without `file.existing.url` silently renders `minio` (`file.tpl:166-175`) and would pass for the wrong reason.
- **Snapshot scope (mechanical sweep).** Exactly the four labels `aws`, `cloud`, `extract`, `extract.ingest`: `resources_test.yaml.snap` gains one `inlineImages: true` line per label, authored together with the test stubs; `golang_test.yaml.snap` and `metrics_test.yaml.snap` change only the `config-hash` value of the same four labels. `app/golang.yaml:65` and `app/metrics.yaml:121` hash the rendered `config-yaml.yaml`, so a label's hash changes exactly when its config changes. Snapshots are patched by hand and verified without `-u`.
- **Hash derivation (values are never typed and never read from a printed render).** The sequence, run from the worktree with helm v3.19.0 first on `PATH`:
  1. After the template edit, run the gate once with its output written to a file: `bash .build/bin/validate-helm.sh > "$SCR/gate.log" 2>&1`, helm v3.19.0 first on `PATH`, `$SCR` a `mktemp -d` directory (task 1.4's command writes the same kind of log and prints only summary lines, so it cannot supply the hashes). The only failing labels must be `aws`, `cloud`, `extract`, `extract.ingest` in `golang_test.yaml` and `metrics_test.yaml`; any other failing label stops the work for investigation, nothing is patched.
  2. From that log, extract only the hash tokens, with the failing suite and label, into a scratch TSV (the surrounding diff holds rendered manifest fragments and is never displayed):
     `awk '/^ FAIL /{n=split($0,a,"\t"); s=a[n]; sub(/.*\//,"",s)} /^\t- [^\t]/{l=substr($0,4)} /^\t+- +config-hash: [0-9a-f]+$/{o=$NF} /^\t+\+ +config-hash: [0-9a-f]+$/{print s "\t" l "\t" o "\t" $NF}' "$SCR/gate.log" | sort -u > "$SCR/hashes.tsv"`
  3. Require exactly one row for each of the four labels in each of the two suites, one old and one new value each, and that each old value occurs in the committed snapshot only inside its own label's block.
  4. Replace old with new inside that label's block of the matching snapshot file, driven by the TSV (an inline `awk` that tracks the current `'<label>':` header), not retyped.
  5. Re-run the gate without `-u`; it must pass, including `verify-helm-snapshot-stability.py` and `verify-helm-snapshots.py`. Then the scope diff in task 1.4: against `git merge-base HEAD origin/main`, the only changed lines anywhere under `src/groundx/tests/__snapshot__` are `inlineImages: true` additions and `config-hash` replacements.
- **Gate versus the privileged-repo convention (conflict recorded, not resolved silently).** `openspec/config.yaml` records from GX-131 that a task check should not execute `validate-helm.sh` in this privileged repo, and that README-only change declared `check: n/a`. This change's instructions require every chart check to run through `bash .build/bin/validate-helm.sh` (or a documented focused `helm template`/`helm lint` form), as the GX-36, FRA-145 and GX-49 task lists did, so task 1.4 does run the gate; its output goes to a temp file, helm v3.19.0 is asserted first, and snapshot files are restored from a pre-run copy if a failing run rewrote them. The reviewer should confirm that choice.
- **Compatibility class (producer).** The key is additive: a worker image that predates the change never reads it, and cashbot-go's config decoder does not run in strict mode (`pkg/config/config.go:94-95@2b9eb1be499caf059aa94818183bbaaf251e00a9`: `yaml.NewDecoder` then `Decode`, no `SetStrict`, `gopkg.in/yaml.v2` imported at `config.go:10`, pinned at v2.4.0 in `go.mod:89@2b9eb1be499caf059aa94818183bbaaf251e00a9`; that module decodes non-strictly unless `SetStrict(true)` is called, `yaml.go:108-109` in `gopkg.in/yaml.v2@v2.4.0`), so an unknown key is not an error. No versioning mechanism is needed. Activation needs a summary-client image that reads the key.
- **No ADR.** The decisions are local to one template and its tests; none is hard to reverse.

## Risks / Trade-offs

- [`helm upgrade` on an `s3` install with the bundled engine rolls every Go-service Deployment and the metrics Deployment once, because their `config-hash` annotations change] → expected and listed in `proposal.md`; no stateful resource is touched, and `helm rollback` rolls the same Deployments back.
- [An operator sets `inlineImages: true` on a remote engine and the worker then sends this install's page-image bytes to that engine's `baseUrl`] → explicit operator choice; the commented `values.yaml` example says so, and the derived default never does it.
- [The hand-patched resources snapshot lines or the regexes drift from the template's real output] → the gate compares them byte-exact, and the unit-test regexes pin the key position.
- [`s3` is matched case-sensitively, so `file.existing.serviceType: S3` renders no key] → same exact-lowercase rule as `upload.service`, which already carries that value to the consumer; no normalisation is added.
- [Task 1.4's check runs the whole gate and takes minutes] → it is the only gate-backed check; the other checks render single templates. If a gate run is killed (for example by a timeout), remove any leftover `files/ocr/gcv-test.json` under both charts before re-running, because the gate refuses to overwrite it.

## Rollout and blast radius

- Order: merge any time. The chart renders the key; nothing reads it until a summary-client image that contains the cashbot-go change is deployed (`Chart.AppVersion` unless `summaryClient.image` is set). Publishing the chart is a separate privileged maintainer step outside this change.
- Affected installs: only `s3` storage with the chart's own engine, or an operator's explicit `inlineImages: true`; each rolls once on upgrade. Rollback: `helm rollback`, or pin `summaryClient.image` to a pre-change image so the worker ignores the key.
- Cross-service coordination and deferred items: see the workspace change's `tasks.md`.
