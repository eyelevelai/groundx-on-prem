# Design — GX-91: Ranker, summary and workspace workers drain on pod termination

Grounded in `proposal.md`. Producer contract shapes confirmed — see the workspace `contract.md` for the `gracePeriod` shape and the external-semantics assumptions. Code citations are at `origin/0.2.8` (`eaa41edc`) unless stated.

## Goals / Non-Goals

- Goal: a terminating `ranker-inference`, `summary-inference` or workspace worker pod receives SIGTERM, stays alive for a 900-second default (overridable per service), stops every Celery worker in the pod together, and gives each a Supervisor stop wait 30 seconds below the pod grace period.
- Non-goal: layout and extract workers (already done), `acks_late`, broker `visibility_timeout`, OOM recovery, `preStop`, the cluster-autoscaler setting, any `ai-server` or `groundx-workspace-runner` change.

## Rollout & removal plans

- Compatibility class: **Additive**, re-confirmed against the code. `ranker.inference.replicas` (`values.schema.json:2237-2250`) and `summary.inference.replicas` (`values.schema.json:910-918`) are `additionalProperties: false` without `gracePeriod`, so adding the property cannot invalidate an existing values file. The workspace `replicas` schema already accepts `gracePeriod` (`values.schema.json:2446-2451`, reached by `cleanup`, `command`, `publish`, `workspace` through `$ref` at `values.schema.json:2483,2484,2626,2631`). The one forward-only edge is that a values file setting the new ranker or summary key fails schema validation on a published 0.2.7 chart; the mechanism is the chart version gate: the harness doc carries a "0.2.8 chart line and later" caveat and its PR merges after the 0.2.8 chart is published.
- Rollout: upgrading restarts `ranker-inference`, `summary-inference` and the five workspace worker Deployments once (container command, `supervisord-hash` annotation). Afterwards a drain waits for in-flight tasks, bounded by the grace period. A summary Deployment with `updateStrategy: Recreate` (an operator setting, `summary-inference.tpl:259-262`) is down for the drain plus model load. Upgrading terminates the old pods under their old spec (30-second grace, no `exec`), so a task in flight during the upgrade can still be lost once; upgrade during low traffic.
- Rollback: redeploy the previous chart (one more restart, grace back to 30 seconds). Remove any `ranker.inference.replicas.gracePeriod` and `summary.inference.replicas.gracePeriod` from values first, or the 0.2.7 schema rejects them.
- No database, secret, SQL, stream or file change. No raw-SQL or DDL mechanism is involved. The SQL-review gate does not apply to this service.
- Staged proof: the local-cluster shutdown test runs before the EKS test, and both before the chart is released (decision 9).

## Decisions

1. **Invariant.** Each `celery_worker_N` program of a ranker, summary or workspace Supervisor config has a stop wait equal to the pod grace period of the service owning that config minus 30 seconds (floor 1) and is a member of the config's one group, and the only rendered output that changes is for those three workload families. The spec scenarios `catches` (an unset grace period never floors the stop wait; a 14-worker group lists all 14; a raised worker count resizes the group) and `must not block` (extract, layout and `layout-inference` render as before; monitor and health stay ungrouped without `stopwaitsecs`) enforce both halves.
2. **`celery.yaml`: drop the per-service conditions.** The grace period is rendered from `replicas.gracePeriod` when set (`templates/app/celery.yaml:94-95`) and otherwise `900` only for the `extract` and `layout` map prefixes (`celery.yaml:96-97`); `exec` is likewise limited to those two prefixes (`celery.yaml:172`). The `else if or (eq $mapPrefix "extract") (eq $mapPrefix "layout")` branch becomes an unconditional `else` and the `{{ if or ... }} exec{{ end }}` becomes a literal `exec`. Every service this template renders (extract, layout, the five workspace workers: `_helpers/app/celery.tpl:3-17`) now has the same behavior, so a later Celery service cannot silently miss the drain. The brainstorm decision (Option B, not an allow-list) is the source; extract and layout output is byte-identical.
3. **`inference.yaml`: the grace period is rendered for every service.** The layout-only guard (`templates/app/inference.yaml:83-85`, `{{- if eq $mapPrefix "layout" }} terminationGracePeriodSeconds: {{ dig "gracePeriod" 900 $rp }}`) loses the `if`. `$rp` for ranker and summary is the map their own `replicas` helpers build from the operator's `replicas` block (`ranker-inference.tpl:149-152`, `summary-inference.tpl:187-190`), so `dig "gracePeriod" 900` reads the override once the schema accepts it; no helper change is needed, as in the layout precedent.
4. **`exec` for ranker and summary through `execOpts`.** `inference.yaml` builds the command as `export PYTHONPATH={{ $wd }}:$PYTHONPATH && {{ $eopts }} supervisord ...` (`inference.yaml:225`), reading `execOpts` from the service settings (`inference.yaml:18`). Only `layout-inference` sets it today (`layout-inference.tpl:203`, `python /app/init-layout.py && exec`). The ranker settings dict (`ranker-inference.tpl:221-236`) and summary settings dict (`summary-inference.tpl:274-292`) each gain `"execOpts" ("exec")`, the keys kept in the existing alphabetical order. The shared command line is untouched.
5. **Stop wait and group in the three Supervisor templates.** Each template computes `$gracePeriod := int (dig "gracePeriod" 900 $replicas)` and `$stopWaitSecs := int (max 1 (sub $gracePeriod 30))`, exactly the layout pattern (`resources/layout-supervisord-conf.yaml:13-15`) and `extract-supervisord-conf.yaml:15-16`. The explicit `900` fallback is what keeps an unset grace period from flooring the stop wait to 1. `stopwaitsecs={{ $stopWaitSecs }}` sits inside the `celery_worker_N` block only (layout places it at `layout-supervisord-conf.yaml:45`). `$replicas` comes from `include "groundx.ranker.inference.replicas" . | fromYaml` in the ranker template (next to its existing `workers` include at `ranker-supervisord-conf.yaml:6`) and the same call to the summary helper in the summary template (`summary-supervisord-conf.yaml:6`), and from `get $svcData "replicas"` in `workspace-supervisord-conf.yaml:6-10`, which already holds the operator's `gracePeriod` (`_helpers/app/workspace-provision.tpl:201-202` and the four sibling helpers). Each template renders one `[group:celery_workers]` section after the programs, `programs=` listing `celery_worker_1..N` (layout pattern: `layout-supervisord-conf.yaml:52-53`); `celery_monitor` and `celery_health` stay outside it. The ranker default of 14 workers comes from `ranker-inference.tpl:210-213`. Blank-line placement in the three configs is verified against the rendered text, not assumed: the ranker and workspace templates emit a `{{ printf "" }}` spacer (`ranker-supervisord-conf.yaml:19`, `workspace-supervisord-conf.yaml:24`), the summary template does not.
6. **Schema.** `gracePeriod: { "type": "integer", "minimum": 1 }` is added to `ranker.inference.replicas` and `summary.inference.replicas` in both schema files, in the existing alphabetical property order. The workspace blocks stay as they are (`{ "type": "integer" }`, no minimum): the proposal does not ask to tighten them, and a workspace `gracePeriod` of 0 keeps rendering as today. `verify_mirrors()` compares `templates/` only, so a task compares the two schema files with `cmp`.
7. **No group priority and no `preStop` until the runtime test says otherwise.** The layout precedent shipped the group without a `priority` (`layout-supervisord-conf.yaml:52-53`). Spike #4 (the group against the ungrouped monitor and health programs) is discharged by the human-run shutdown test (decision 9). Only if that test shows a worker starting a task after SIGTERM because Supervisor stops `celery_monitor` or `celery_health` first does this design add a `priority` to the group, with its own RED test in the same apply pass; the committed stubs assert no priority, so a test result that needs one is a design amendment, not a silent addition.
8. **Summary solo pool.** `summary-supervisord-conf.yaml:22` runs `--pool=solo`, and the summary app installs its own SIGTERM and SIGINT handlers at import (`ai-server` `summary/tasks/inference.py:44-45` at `40623af3be753db5f3808bbdf222a3ea6d15a21e`), which set a stop flag for its lock-acquisition loop. Whether that coexists with Celery's warm shutdown is not decided from the chart. Spike #6 is the shutdown test on the real summary image; if it fails, the pipeline stops for a plan amendment on an `ai-server` change, which is out of scope here.
9. **Shutdown proof is human-run, not a pipeline check.** `groundx-on-prem` is a PRIVILEGED repo, so the pipeline never executes cluster commands. The local-cluster test and then the validation-infra EKS test run the real ranker image (14 workers), the summary image and one workspace worker, SIGTERM each pod while a task runs, and record the evidence in the change folder. It must fail on the chart before this change. Spike #7 (Kombu restores reserved-but-unstarted messages on warm shutdown at once instead of after the 3600-second default `visibility_timeout`) is read from the same test and may be recorded as an accepted risk, since the proposal keeps `visibility_timeout` out of scope.
10. **Tests.** New explicit-assert cases go into the suites that render the same templates: `src/groundx/tests/celery_test.yaml` (workspace exec, default and overridden grace, stop wait, floor, group, retargeted startup-command case) and `src/groundx/tests/inference_test.yaml` (ranker and summary exec, grace, override, floor, 14-worker group, raised worker counts, zero-grace schema rejection). Each asserts the fix explicitly, not through a snapshot alone, because the five snapshots are hand-patched in this change and a snapshot alone can freeze a broken render as golden. `inference_test` runs singly without extra setup; `celery_test` needs the throwaway Google-OCR credentials file the gate generates (`.build/bin/validate-helm.sh:86-104`), so its check writes the same bytes and removes them afterwards. The case "workspace workers keep their existing startup command" (`celery_test.yaml:411`) asserted the old no-`exec` command and is renamed "workspace workers replace the shell with supervisord" with the `exec` command. Test names and assertions carry intent; no code comments.
11. **Snapshots hand-patched, never regenerated.** `celery_test`, `inference_test`, `ranker_test`, `workspace_test` and `resources_test` snapshot blocks change for the affected Deployments (command, `terminationGracePeriodSeconds`, `supervisord-hash`) and Supervisor config maps. They are patched from the diff a plain `helm unittest` prints, never with `-u`, verified with a plain `helm unittest` and `.build/bin/verify-helm-snapshots.py`, in a commit separate from the template and test changes. Hash values come from the render, never typed. The new test cases use explicit asserts, so they add no snapshot block.
12. **Record hygiene and docs.** `values.yaml` gets a short comment above the `replicas:` block of `ranker.inference`, `summary.inference` and the five workspace workers naming the 900-second default and the `gracePeriod` override; no existing layout comment exists to copy, and operator-facing documentation beyond that is the harness `values-yaml.md` change in the second PR. The autoscaler caveat (effective grace is the smaller of `gracePeriod` and `--max-graceful-termination-sec`, default 600 seconds, as recorded in the archived GX-66 design, decision 9, which cites kubernetes/autoscaler `cluster-autoscaler/FAQ.md:1083` at `22575f5c8af3edd9a10ca10d7d9edef68d2982cd`) is documented, not changed.
