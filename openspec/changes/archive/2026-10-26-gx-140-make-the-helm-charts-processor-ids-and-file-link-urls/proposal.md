## Why

GroundX Cloud cannot run on this chart yet, because two settings it needs are fixed. First, the chart writes the 13 processor ID lists in cashbot-go's `config.yaml` as literal text (`src/groundx/templates/resources/config-yaml.yaml:603-616` at `895ca7a35`), plus a fixed `processorID: 1` skip-generate entry in `mode: ingest` (`:620-624`). cashbot-go takes each processor's type and settings from the database row with that ID. A fresh database gets the 13 system rows in exactly the chart's ID order (cashbot-go `pkg/cbdb/mysql.go:110-124` at `9c12fb5fc3`), so new installs work. The GroundX Cloud database maps those IDs to other processor types, according to the read-only production query recorded in the ticket on 2026-10-23. Second, for existing storage the chart derives `upload.baseUrl` and `upload.bucketUrl` from the same host (`config-yaml.yaml:711-715`) and never renders an `uploadGroundx` section. GroundX Cloud serves file links from `https://upload.eyelevel.ai` and `https://upload.groundx.ai`. Today the only way to set a separate link host is the file-access gateway (`fileAccess.enabled: true`, `config-yaml.yaml:707-709`), and GroundX Cloud does not run the gateway.

Moving GroundX Cloud onto the published chart (GX-4) needs both settings: the processor IDs so documents get processed and indexed, and the link URLs so existing file links keep working.

## What Changes

- New optional `cluster.processors` value. It covers the 13 lists (`convert`, `extract`, `layout`, `map`, `saveFile`, `skipConvert`, `skipGenerate`, `skipLayout`, `skipMap`, `skipSummarize`, `summarize`, `summarizeChunks`, `summarizeSections`), and each list it sets replaces that list's default. Any list left unset keeps its current default. In `mode: ingest`, the generated `processors.extraPostDefaults` skip-generate entries use the configured `skipGenerate` IDs instead of the fixed `1`.
- New optional `file.publicUrl` value. It sets only `upload.baseUrl`. `upload.baseDomain` and `upload.bucketUrl` keep the storage host.
- New optional `file.groundxPublicUrl` value. When set, the chart renders an `uploadGroundx` section that matches `upload` field for field, except that `baseUrl` is the alias. When it is not set, no `uploadGroundx` section renders, so cashbot-go keeps using `upload` for GroundX links as it does today (cashbot-go `pkg/partner/handler.go:106-109` at `9c12fb5fc3`).
- The render fails with a clear message if `fileAccess.enabled: true` is combined with either URL key. With the gateway on, `fileAccess.publicUrl` already controls `upload.baseUrl`. With the gateway on, cashbot-go also checks the gateway against `uploadGroundx` whenever that section has a base URL, and fails closed if the check does not pass (cashbot-go `pkg/cbdb/file_access.go:174-179` at `324a6fc78c`). The alias error must not suggest `fileAccess.trustedOrigins` as a replacement. The gateway's own behavior does not change.
- If none of the new keys is set, the rendered config stays byte-identical. That covers the `processors` block, additional pre-processors, ingest-mode defaults, and the `upload` section, and no `uploadGroundx` section renders. No existing helm-unittest snapshot changes.
- `values.yaml` gets short comments for each key: its default and that a new install does not need it; the `cluster.processors` comment also says GroundX Cloud must set it. All three keys go into `values.schema.json`, which rejects unknown keys. Every edit is copied by hand into the `helm/` mirror, so the two schemas and the two `values.yaml` files stay byte-identical.
- `docs/agents/private-file-access.md` gets a one-line note that both URL keys are rejected when the gateway is on.
- The chart version and image tags do not change. Publishing the chart release is out of scope.

## Capabilities

### New Capabilities
- `processor-id-overrides`: an optional `cluster.processors` map that replaces any of the 13 default processor ID lists in the rendered `config.yaml`, drives the ingest-mode skip-generate entry, and changes nothing when omitted.
- `file-link-urls`: optional `file.publicUrl` and `file.groundxPublicUrl`. The first sets the `upload` link host and the second adds an `uploadGroundx` alias section, both without the file-access gateway. Either key is rejected at render when the gateway is enabled, and omitting both leaves the `upload` section unchanged.

### Modified Capabilities
- None. No existing spec under `openspec/specs/` covers processor IDs or upload link URLs. The file-access gateway requirements belong to the active, unarchived `protect-hosted-file-access` change, and this change leaves them unchanged.

## Impact

- **Code:** `src/groundx/templates/resources/config-yaml.yaml`, a processor helper next to `groundx.preProcessors` in `templates/_helpers/main.tpl`, the existing `groundx.fileAccess.validate` list in `templates/_helpers/app/file-access.tpl`, `values.yaml`, `values.schema.json`, and the hand-copied `helm/` versions of each, plus two `MIRRORED_FILES` entries in `.build/bin/verify-storage-contract.py` so the gate byte-compares the two values files. New render cases go in the existing `tests/resources_test.yaml` and `tests/file_settings_test.yaml`. There are no new test files and no snapshot changes. `.build/bin/validate-helm.sh` gates the change.
- **Consumers:** cashbot-go reads the rendered `config.yaml` and needs no change, because it already reads `processors`, `upload.baseUrl` / `upload.bucketUrl`, and `uploadGroundx` (`pkg/config/api.go:161`, `pkg/utility/url.go:360`, `:378` at `9c12fb5fc3`). groundx-studio-harness documents the new keys in a separate, later change.
- **Blast radius:** this applies only to installs that upgrade to a chart release that contains this change. Such an install renders the same `config.yaml` unless the operator sets a new key, so an upgrade with unchanged values changes no config. The risk comes from setting a key. A processor ID that points at the wrong row makes cashbot-go run the wrong processor type on new documents. This change does not detect or prevent that, because the chart cannot see the database. A wrong link URL makes cashbot-go stop recognizing its own stored links. Both URL keys will use the schema pattern `^$|^https?://[A-Za-z0-9.-]+(:[0-9]{1,5})?$` (scheme, hostname, optional port), so a URL with a path, credentials, query string, fragment, space, or a colon other than the port separator is rejected before rendering. `file.signingEndpoint` keeps its existing pattern.
- **Environments:** the chart deploys self-hosted customer clusters and, after GX-4, GroundX Cloud. This change does not touch dev, staging, or production values. Applying the overrides to the GroundX Cloud deployment is out of scope.
- **Data and stateful resources:** none. The `processors` table, storage buckets, and existing file links are not modified. The new keys only change which IDs and URLs the config points at.
- **Rollback / roll-forward:** to roll back, remove the keys, or `helm rollback` to the previous revision, and the rendered config reverts to the defaults. To roll forward after a wrong value, correct it and run `helm upgrade`. Documents processed while a wrong processor ID was set are not reprocessed automatically.
- **Open design questions:** none. The brainstorm and plan gate already decided key names, gateway interaction, and the default-path proof.
