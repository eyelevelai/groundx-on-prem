# Tasks: GX-152 configurable migration Job limits and a GitOps opt-in

Checks run from the repo root via `bash -c`. Set `GX_ON_PREM_HELM` to a Helm v3.19.0 binary with the pinned helm-unittest plugin; every Helm check stops with an error if it is unset or another version. Suite checks run on a `mktemp -d` copy of the chart with the gate's throwaway Google-OCR fixture written in the same format as `.build/bin/validate-helm.sh`, so the worktree's snapshots are never rewritten. Only task 3.1 runs `helm unittest -u`, on a scratch copy, to prove the hand-edited snapshot matches the regenerator's output as parsed data; it needs `ACCEPTANCE_CHECK_TIMEOUT` of at least 300 s. No check prints a rendered manifest. "Base" in the checks is `git merge-base HEAD origin/0.3.0` (`8f99d2ba` when this change was written). Task 3.2 runs the full chart gate, a script inside this privileged repo; it runs only through the orchestrator's acceptance checks, which the human approves, and needs `ACCEPTANCE_CHECK_TIMEOUT` of at least 900 s.

Mirror rule: every template, `values.yaml` and `values.schema.json` edit under `src/groundx/` is copied byte-for-byte into `helm/` in the same task. `Chart.yaml` does not change.

The `golang_test.yaml` cases and the `validate-helm.sh` migration assertions these checks rely on are already written and fail on the unchanged chart.

## Rollout sequence (no secret changes, no SQL, no manual ops in this repo)

1. Release with the next chart cut from `0.3.0`. Every Helm upgrade with a Go workload then renders the migration Job with a 3600 s deadline and 2 retries; nothing else in the rendered Job changes for unchanged values.
2. Argo CD users set `groundx.migration.gitOps: true` per Application once the database, credentials, service account and pull Secrets exist.
3. The groundx-studio-harness documentation change merges only after that chart release is published.
