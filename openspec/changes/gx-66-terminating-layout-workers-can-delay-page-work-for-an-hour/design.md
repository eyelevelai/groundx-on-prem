# Design — GX-66: Layout workers drain on pod termination

Grounded in `proposal.md`. Producer contract shapes confirmed — see the workspace `contract.md` for the `gracePeriod` shape and the external-semantics assumptions.

## Goals / Non-Goals

- Goal: a terminating layout Celery worker or `layout-inference` pod receives SIGTERM, keeps its pod alive for a 900-second default (overridable per service), and gives Supervisor a stop wait of 30 seconds less.
- Non-goal: ranker inference, summary inference and workspace workers (GX-91); `preStop`; Redis `visibility_timeout`; OOM recovery (GX-61).

## Rollout & removal plans

- Compatibility class: **Additive** (optional `gracePeriod` key; defaults only lengthen the drain). Confirmed against the code: `layout.<svc>.replicas` is `additionalProperties: false` with `desired`/`max`/`min` at `origin/0.2.7` (`ef227964`), so adding a property cannot invalidate an existing values file. The mechanism for the one forward-only edge — a values file that sets `gracePeriod` fails schema validation on an older chart — is the chart version gate: the harness doc carries a "0.2.7 and later" caveat and its PR merges after 0.2.7 publishes.
- Rollout: upgrading to a chart with this change restarts the six layout Deployments once (container command and `supervisord-hash` annotation change). `layout-inference` with `updateStrategy: Recreate` can take up to its grace period to roll when a worker is mid-task. Ranker, summary, workspace, extract and Go services are not restarted.
- Rollback: redeploy the previous chart version (one more rolling restart of the six Deployments, grace back to the 30-second Kubernetes default). Remove any `layout.<svc>.replicas.gracePeriod` from values first, or the older chart rejects them.
- No database, secret or SQL change. The SQL-review gate does not apply to this service.

## Decisions

1. **Invariant.** Each layout `celery_worker_N` stop wait is the pod grace period of the service that owns that Supervisor config minus 30 seconds (floor 1), and the only workloads whose shutdown output changes are the five layout Celery workers and `layout-inference`. Spec scenarios `catches` (stop wait derived from an unset value; ranker inference gaining a grace period) and `must not block` (ranker, summary, workspace, extract unchanged) enforce both halves.
2. **Gate on the layout map prefix inline, no new helper.** `celery.yaml` already branches on `$mapPrefix "extract"` for the 900 default and for `exec`; layout joins those two conditions (`or (eq $mapPrefix "extract") (eq $mapPrefix "layout")`). `inference.yaml` gets one new block gated on `eq $mapPrefix "layout"`. This copies the extract precedent (`19e5b712`, `d3c99a7b`) without abstracting a helper for two call sites.
3. **Override needs no helper change.** `celery.yaml` renders `replicas.gracePeriod` through `hasKey $rp "gracePeriod"` for every worker, and each layout `groundx.layout.<svc>.replicas` helper starts from the operator's own `replicas` map, so the key reaches the template once the schema accepts it. The extract helpers' extra `set $cfg "gracePeriod"` line is not copied. `inference.yaml` reads the same map with `dig "gracePeriod" 900 $rp`.
4. **`exec` for layout-inference through `execOpts`.** `inference.yaml` builds its command as `... && {{ $eopts }} supervisord ...`, and only `layout-inference` sets `execOpts` (`python /app/init-layout.py &&`). Extending that one value to `python /app/init-layout.py && exec` puts `exec` after init and leaves the shared command line, and therefore the ranker and summary output, byte-identical.
5. **Stop wait computed in the layout Supervisor template.** `layout-supervisord-conf.yaml` reads `replicas` from the same per-service settings it already iterates, with `dig "gracePeriod" 900`, and applies `max 1 (sub grace 30)` exactly as `extract-supervisord-conf.yaml` does. The 900 fallback is explicit so `layout-inference`, which shares this template, never evaluates an unset grace period (which would floor the stop wait at 1 second). `stopwaitsecs` sits inside the `celery_worker_N` block only; `celery_monitor` and `celery_health` are untouched.
6. **Schema.** `gracePeriod: { "type": "integer", "minimum": 1 }` is added to the six worker `replicas` blocks in both schema files, in the existing alphabetical property order. `layout.api` is a gunicorn service, not a worker, and does not gain it. `verify_mirrors()` byte-compares `templates/` only, so a task compares the two schema files directly.
7. **No `preStop`.** The user chose to rely on Celery's warm shutdown and to check "takes no new task after SIGTERM" in the uncommitted runtime test; a positive finding is escalated, not patched here.
8. **Multi-worker pods (open, decided by the runtime test).** If a `layout.map.workers: 2` runtime test shows Supervisor stops `celery_worker_1` and `celery_worker_2` one after another, the `celery_worker` programs are grouped; otherwise config stays per-program. The spec asserts only that both programs carry the stop wait. The apply phase returns the runtime result to the main loop as an escalation before any group change is made, and the outcome is then recorded here and in the PR body.
9. **Autoscaler caveat.** On cluster-autoscaler scale-down the effective grace is the smaller of `gracePeriod` and the autoscaler's `--max-graceful-termination-sec`, whose documented default is 600 seconds (kubernetes/autoscaler `cluster-autoscaler/FAQ.md:1083` at `22575f5c8af3edd9a10ca10d7d9edef68d2982cd`). The chart does not change the autoscaler; the harness doc carries the same note, and the validation-cluster value is read during the cluster run.
10. **Tests.** The new coverage is one snapshot-free suite, `src/groundx/tests/layout_shutdown_test.yaml`, that runs against the source chart, which owns the schema and templates, plus one `helm/tests/layout_grace_period_test.yaml` case that renders `gracePeriod` through the mirror chart so the mirror schema is exercised on every CI run (the same `helm/tests/` placement as `layout_ocr_timeout_test.yaml`). It is a new file rather than additions to `celery_test`, `inference_test` and `resources_test` because those suites hold snapshot cases and cannot run singly for a per-task check (a bare run of `celery_test` fails its OCR case without the gate's credentials fixture, and `-u` regeneration is banned, see AGENTS.md). The existing `celery_test` case "non-extract workers keep their existing startup command" asserts that `layout-correct` has no `exec`; it is retargeted to a workspace worker and renamed "workspace workers keep their existing startup command", which still proves the non-extract, non-layout command is unchanged.
11. **Snapshots hand-patched.** The affected `__snapshot__` blocks (layout Deployments' command, `terminationGracePeriodSeconds`, `supervisord-hash`; layout Supervisor config maps; `layout-inference` in the inference snapshots) are hand-patched from the diff `helm unittest` prints without `-u`, in a commit separate from the template and test changes. Hash values come from the render, never typed. `workspace_test`, `ranker_test`, `extract_test` and the ranker and summary documents stay byte-identical.
12. **Record hygiene.** No repo doc lists layout `replicas`; the operator-facing documentation is the harness `values-yaml.md` change in the second PR. `config.yaml` `context:` still says to regenerate snapshots with `helm unittest -u`, which contradicts AGENTS.md; a correcting line is appended.
